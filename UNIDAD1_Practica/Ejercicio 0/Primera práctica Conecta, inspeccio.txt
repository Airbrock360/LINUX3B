Evidencia mínima por actividad: 1) comando o acción, 2) salida relevante, 3) interpretación técnica y 4) decisión o siguiente prueba. Las salidas están recortadas a las líneas relevantes.
Actividad 1. Identificar distribución y kernel
1. Comando o acción
cat /etc/os-release y uname -r
2. Salida relevante
alex@Ubuntu:~$ cat /etc/os-release
PRETTY_NAME="Ubuntu 26.04 LTS"
VERSION="26.04 (Resolute Raccoon)"
ID=ubuntu
ID_LIKE=debian
alex@Ubuntu:~$ uname -r
7.0.0-42-generic
3. Interpretación técnica
El sistema es Ubuntu 26.04 LTS, con nombre en clave Resolute Raccoon; LTS significa soporte a largo plazo. La línea ID_LIKE=debian indica que pertenece a la familia Debian, por lo que usa paquetes .deb y el gestor apt. El kernel es 7.0.0-42-generic: versión 7.0 de Linux, revisión 42 del paquete de Ubuntu y variante generic, pensada para equipos y máquinas virtuales de uso general.
4. Decisión o siguiente prueba
Como es un sistema de la familia Debian, instalaré el software con apt. Siguiente prueba: uname -a para ver además el nombre del equipo y la arquitectura.
Actividad 2. Confirmar usuario, grupos y ruta
1. Comando o acción
whoami, id y pwd
2. Salida relevante
alex@Ubuntu:~$ whoami
alex
alex@Ubuntu:~$ id
uid=1000(alex) gid=1000(alex) groups=1000(alex),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),111(lpadmin),114(lxd)
alex@Ubuntu:~$ pwd
/home/alex
3. Interpretación técnica
Estoy trabajando como el usuario alex, con uid=1000, que es el primer usuario normal creado en el sistema (no es root, cuyo uid es 0). Su grupo principal es alex y pertenece a otros grupos con permisos especiales: sudo permite ejecutar comandos como administrador, adm permite leer los registros del sistema y lxd permite administrar contenedores, un privilegio alto que conviene tratar con cuidado. La ruta actual /home/alex es el directorio personal del usuario.
4. Decisión o siguiente prueba
Como pertenezco al grupo sudo, puedo hacer tareas de administración usando sudo sin entrar como root. Siguiente prueba: sudo whoami, que debe responder root para confirmar que el permiso funciona.
Actividad 3. Examinar archivos y permisos
1. Comando o acción
ls -la, ls -la /etc/shadow y stat /etc/shadow
2. Salida relevante
alex@Ubuntu:~$ ls -la
total 100
drwxr-x--- 19 alex alex 4096 Sep 18 09:56 .
drwxr-xr-x  3 root root 4096 Aug 17 21:37 ..
-rw-------  1 alex alex 7407 Nov  5 19:42 .bash_history
drwx------  2 alex alex 4096 Aug 17 21:47 .ssh
drwxr-xr-x  2 alex alex 4096 Aug 17 21:51 Desktop
drwxrwxr-x  5 alex alex 4096 Nov  5 14:26 scripts
alex@Ubuntu:~$ ls -la /etc/shadow
-rw-r----- 1 root shadow 1349 Oct 30 09:49 /etc/shadow
alex@Ubuntu:~$ stat /etc/shadow
  File: /etc/shadow
  Size: 1349      Blocks: 8     IO Block: 4096   regular file
Device: 8,2   Inode: 1575658   Links: 1
Access: (0640/-rw-r-----)  Uid: (    0/    root)   Gid: (   42/  shadow)
Access: 2026-11-05 19:31:19
Modify: 2026-10-30 09:49:07
Change: 2026-10-30 09:49:07
 Birth: 2026-10-30 09:49:07
3. Interpretación técnica
ls -la muestra los archivos y carpetas del directorio actual (mi home), incluidos los ocultos, que empiezan con punto. La primera columna indica el tipo (d directorio, - archivo) y los permisos en tres bloques: dueño, grupo y otros. El total 100 son los bloques de disco que ocupan esos archivos, no la cantidad de archivos. Mi home es drwxr-x---, así que otros usuarios no pueden entrar; .ssh es drwx------ y .bash_history es -rw-------, o sea, solo yo puedo acceder a ellos.
En /etc/shadow los permisos -rw-r----- equivalen a 640: root lee y escribe, el grupo shadow solo lee y los demás no tienen acceso. Ese archivo guarda los hashes de las contraseñas, por eso está tan restringido. stat confirma el dueño root, el grupo shadow (gid 42), el tamaño de 1349 bytes, el inodo y las fechas: Access es el último acceso, Modify el último cambio del contenido, Change el último cambio de metadatos y Birth la creación.
4. Decisión o siguiente prueba
Como alex no pertenece al grupo shadow, no debería poder leer ese archivo. Siguiente prueba: cat /etc/shadow, que debe responder Permission denied, y compararlo con /etc/passwd, que sí es legible por todos.
Actividad 4. Observar proceso y servicio
1. Comando o acción
ps aux | head -15, systemctl status y systemctl status ssh
2. Salida relevante
alex@Ubuntu:~$ ps aux | head -15
USER   PID %CPU %MEM    VSZ   RSS TTY STAT START TIME COMMAND
root     1  1.3  0.3  25752 16632 ?   Ss   19:48 0:02 /usr/lib/systemd/systemd --switched-root --system --deserialize=55
root     2  0.0  0.0      0     0 ?   S    19:48 0:00 [kthreadd]
alex@Ubuntu:~$ systemctl status
● Ubuntu
    State: running
    Units: 560 loaded (incl. loaded aliases)
     Jobs: 0 queued
   Failed: 0 units
    Since: Thu 2026-11-05 19:48:04 CST
alex@Ubuntu:~$ systemctl status ssh
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/usr/lib/systemd/system/ssh.service; enabled; preset: enabled)
     Active: active (running) since Thu 2026-11-05 19:48:09 CST
   Main PID: 1482 (sshd)
nov 05 19:48:09 Ubuntu sshd[1482]: Server listening on 0.0.0.0 port 22.
3. Interpretación técnica
ps aux lista todos los procesos del sistema, con su usuario, PID, uso de CPU y memoria, estado, hora de inicio y comando. El PID 1 es systemd, el primer proceso y el administrador de servicios; el PID 2 es kthreadd, que crea los hilos del kernel (los nombres entre corchetes). Todos arrancaron a las 19:48, que es la hora del último inicio del sistema.
systemctl status muestra el estado global: State: running con Failed: 0 units y Jobs: 0 queued indica que el sistema está sano y sin servicios fallidos (si alguno fallara, diría degraded). El servicio ssh aparece enabled (arranca con el sistema) y active (running), con el proceso principal sshd de PID 1482 escuchando en el puerto 22.
4. Decisión o siguiente prueba
Como el servicio ssh está activo y no hay unidades fallidas, no hace falta reiniciar nada. Siguiente prueba: confirmar con ss -ltnp que el puerto 22 realmente está abierto y pertenece a sshd.
Actividad 5. Relacionar puerto y evidencia
1. Comando o acción
sudo ss -ltnp y sudo journalctl -u ssh -n 10
2. Salida relevante
alex@Ubuntu:~$ sudo ss -ltnp
State   Local Address:Port   Process
LISTEN  0.0.0.0:22           users:(("sshd",pid=1482,fd=3),("systemd",pid=1,fd=97))
LISTEN  0.0.0.0:80           users:(("nginx",pid=1610,fd=5), ...)
LISTEN  192.168.0.26:53      users:(("named",pid=1536,fd=57))
LISTEN  127.0.0.53%lo:53     users:(("systemd-resolve",pid=426,fd=17))
LISTEN  127.0.0.1:631        users:(("cupsd",pid=1463,fd=7))
LISTEN  [::]:22              users:(("sshd",pid=1482,fd=4),("systemd",pid=1,fd=98))
alex@Ubuntu:~$ sudo journalctl -u ssh -n 10
nov 05 19:42:41 Ubuntu sshd[1499]: Received signal 15; terminating.
nov 05 19:42:41 Ubuntu systemd[1]: ssh.service: Deactivated successfully.
-- Boot bc017439ebd5411ea3066bd44d6b018d --
nov 05 19:48:09 Ubuntu sshd[1482]: Server listening on 0.0.0.0 port 22.
nov 05 19:48:09 Ubuntu systemd[1]: Started ssh.service - OpenBSD Secure Shell server.
3. Interpretación técnica
ss -ltnp muestra los puertos TCP en escucha (-l escuchando, -t TCP, -n números en lugar de nombres, -p el proceso dueño; por eso necesita sudo). La dirección 0.0.0.0 significa que escucha en todas las interfaces, mientras que 127.0.0.1 solo acepta conexiones locales. Los puertos se relacionan con sus servicios así: el 22 con sshd (acceso remoto), el 80 con nginx (la página web), el 53 en 192.168.0.26 con named (el servidor DNS BIND) y el 631 con cupsd (impresión, solo local).
La evidencia coincide entre comandos: el PID 1482 de sshd en ss es el mismo Main PID de systemctl status ssh. En el registro de journalctl se ve que el servicio se detuvo de forma normal a las 19:42:41 (señal 15, Deactivated successfully), la máquina arrancó de nuevo (-- Boot --) y a las 19:48:09 sshd volvió a quedar escuchando en el puerto 22, justo la hora que aparece en systemctl status.
4. Decisión o siguiente prueba
El puerto 22 abierto y el servicio activo confirman que el acceso remoto está disponible. Siguiente prueba: conectarme desde Windows con ssh alex@192.168.0.26 y volver a correr sudo journalctl -u ssh -n 10 para ver en el registro la línea de la conexión aceptada.
Conclusión
Con estos comandos identifiqué el sistema (Ubuntu 26.04 LTS, kernel 7.0.0-42-generic), mi usuario y sus grupos, los permisos de archivos sensibles como /etc/shadow, el estado de los procesos y servicios con systemd, y relacioné el puerto 22 con sshd usando ss, systemctl y journalctl como evidencia cruzada.
